LodyLand utilise plusieurs sources YAML :

Type Fragments éditables Fichier merged utilisé par le jeu Script de merge
Cards app/data/cards/**.yml app/data/cards.yml app/data/cards/normalize_cards_yaml.py
Crafts app/data/crafts/**.yml app/data/crafts.yml app/data/crafts/normalize_crafts_yaml.py
Items (tools, weapons, misc…) app/data/items/*.yml pas de merge : lus directement –
Ressources récoltables app/data/resources.yml fichier unique –
Source of truth : tu édites toujours les fragments dans app/data/cards/, app/data/crafts/, app/data/items/ et app/data/resources.yml. Les fichiers mergés cards.yml et crafts.yml sont générés.

1. Structure des dossiers

1.1 Cards

app/data/cards/
├── boosts/
├── lands/
├── packs/
├── craft/
│   ├── access.yml          # cartes d'accès aux stations de craft
│   └── recipes/
│       ├── resources.yml   # cartes "recipe" pour crafts de ressources
│       ├── tools.yml       # cartes "recipe" pour crafts d'outils
│       └── weapons.yml     # cartes "recipe" pour crafts d’armes
├── debug/
├── normalize_cards_yaml.py
└── _README.md / cards_readme.html

Le script normalize_cards_yaml.py scanne tous les fragments et génère app/data/cards.yml. Tu peux te référer à cards_readme.html pour les détails complets sur les champs.

1.2 Items & ressources

app/data/
├── items/
│   ├── resources.yml   # items de type "resource"
│   ├── tools.yml       # items de type "tool"
│   ├── weapons.yml     # items de type "weapon"
│   └── misc.yml        # items divers (potions, consommables, etc.)
└── resources.yml       # définition des ressources récoltables par les lands

Les items sont chargés par craft_defs.py (et d’autres services). Ils sont organisés par fichier, mais tout se retrouve dans un seul gros dict côté Python.

1.3 Crafts

app/data/crafts/
├── craft_base/
│   ├── resources.yml   # recettes de base → simple craft_table
│   ├── tools.yml       # recettes outils de base
│   ├── weapons.yml     # recettes armes de base
│   └── misc.yml        # recettes divers
├── forge_base/
│   └── resources.yml   # recettes de forge
├── craft_medium_table/
├── craft_advanced_table/
├── alchemy_base/
├── cooking_base/
├── craft_building/
└── normalize_crafts_yaml.py

Chaque sous-dossier représente une station de craft ou une famille de recettes (forge, alchimie, etc.).

2. Définir des items (resources, tools, weapons…)

Les items “inventaire” sont définis dans app/data/items/*.yml. Structure attendue dans chaque fichier : 

# app/data/items/tools.yml
items:
  tool_wooden_axe:                # slug interne
    key: tool_wooden_axe          # clé globale, utilisée partout
    label: Wooden Axe
    icon: /static/assets/img/items/tools/wooden_axe.png

    kind: tool                    # tool | weapon | resource | misc | consumable...
    category: woodcutting         # pour ton futur système de skills

    description: >
      A basic wooden axe. Allows you to chop trees faster.

    stackable: false
    max_stack: 1

    base_sell_price: 30
    base_buy_price: 0

    unlock_default:
      type: card                  # ou land, quest, etc.
      key: recipe_tool_wooden_axe # clé d'une carte ou d'un autre déclencheur

    tags: [axe, basic]

2.1 Champs principaux

ChampTypeUsage
key string Identifiant global de l’item (doit être unique dans tous les fichiers items).
label string Nom affiché en jeu (pour l’instant en anglais, futur système de langues s’appuiera dessus).
kind string resource, tool, weapon, misc, etc.
category string Catégorie gameplay (ex: woodcutting, fishing…).
icon string Chemin d’icône (32x32 ou 64x64 PNG) sous /static.
stackable, max_stack bool + int Gestion de la pile en inventaire.
base_sell_price, base_buy_price int Prix par défaut (shop / trades).
unlock_default mapping Comment l’item se débloque par défaut (carte, land, quête…).
tags list[str] Mots clés libres pour filtres, logiques futures, etc.

2.2 Ressources récoltables : app/data/resources.yml

Les ressources générées par les lands (clic, cooldown…) sont dans app/data/resources.yml : 

resources:
  - key: branch
    label: Branches
    description: Une branche tombée d'un arbre...
    icon: /static/assets/img/resources/branch.png

    unlock_min_level: 0
    base_cooldown: 10.0
    base_sell_price: 2
    enabled: true
    unlock_description: Toujours accessible (niveau 0).

Ce fichier est utilisé par le système de récolte / lands.
Les crafts, eux, regardent les items (dans app/data/items) pour les clés de ressources de type resource utilisées en sortie.

3. Rappel rapide : cartes d’accès & recettes

Les cartes sont documentées en détail dans app/data/cards/cards_readme.html. Ici on ne rappelle que ce qui est pertinent pour les crafts.

3.1 Cartes d’accès au craft

Exemple de carte permettant d’accéder à une station de craft (ou d’upgrader la table) : 

# app/data/cards/craft/access.yml
- key: access_craft_table_basic
  enabled: true
  card_type: craft_access
  card_category: craft
  card_label: Craft Table — Tier 1
  card_description: Unlocks the basic 1x3 craft table.
  card_image: /static/assets/img/cards/craft/card_access_craft_table_basic.png
  card_rarity: basic

  card_gameplay:
    station_key: craft_table_base
    max_tier: 1

Le champ important côté craft est généralement card_gameplay.station_key ou un équivalent : il connecte la carte à une station de craft et/ou à un niveau de grille.

3.2 Cartes de recettes

Chaque craft doit être protégé par une carte de type “recipe” via unlock.recipe_card_key. 

# app/data/cards/craft/recipes/tools.yml
- key: recipe_tool_wooden_axe
  enabled: true
  card_type: craft_recipe
  card_category: craft
  card_label: Recipe — Wooden Axe
  card_description: Recipe to craft a Wooden Axe.
  card_image: /static/assets/img/cards/recipes/card_recipe_wooden_axe.png

  card_gameplay:
    target_item_key: tool_wooden_axe

  shop:
    prices:
      - coins: 50
        diams: 0
        resources: {}
    show_in_main_shop: true
La clé recipe_tool_wooden_axe sera référencée dans le bloc unlock.recipe_card_key côté craft.

4. Définir des crafts

Les crafts sont définis dans les fragments sous app/data/crafts/**.yml, puis mergés en app/data/crafts.yml par normalize_crafts_yaml.py.

4.1 Format général d’un fragment

Deux formats sont acceptés :

  • Ancien format (avec bloc crafts:) : 
# app/data/crafts/craft_base_table.yml
crafts:
  tool_wooden_axe:
    key: tool_wooden_axe
    station_key: craft_table_base
    ...
  • Nouveau format “plat” : le top-level est directement slug -> craft_cfg. 
# app/data/crafts/craft_base/resources.yml
tool_wooden_axe:
  key: tool_wooden_axe
  station_key: craft_table_base
  ...

Le normalizer supporte les deux, mais il est conseillé d’utiliser le format plat pour les nouveaux fichiers.

4.2 Exemple complet de craft

# app/data/crafts/craft_base/tools.yml
tool_wooden_axe:
  key: tool_wooden_axe
  station_key: craft_table_base

  required_grid:
    tier: 1                  # 1x3 de base

  output:
    kind: tool
    key: tool_wooden_axe
    quantity: 1

  recipe:
    pattern:
      - "BBS"
    legend:
      B:
        kind: resource
        key: branch
        quantity: 1
      S:
        kind: resource
        key: stick
        quantity: 1

  craft_time_seconds: 8
  xp_reward: 5

  unlock:
    recipe_card_key: recipe_tool_wooden_axe
    min_level: 2

  enabled: true

4.3 Champs obligatoires côté craft

ChampTypeDescription
key string Clé de l’item crafté (doit exister dans app/data/items/*.yml ou être alignée avec future définition).
station_key string Identifie la station de craft (ex: craft_table_base, forge_base…).
required_grid.tier int Niveau de grille requis (1→1x3, 2→2x3, 3→3x3, etc.).
output mapping Type & quantité du résultat (kind + key + quantity).
recipe.pattern list[str] Pattern de craft (lignes de caractères, . = vide).
recipe.legend dict Mapping symbole → { kind, key, quantity }.
unlock dict Doit contenir un recipe_card_key existant dans cards.yml.
craft_time_seconds number Durée de craft en secondes.

4.4 Vérifications automatiques

normalize_crafts_yaml.py fait les checks suivants :

  • Syntaxe YAML correcte (sinon erreur explicite).
  • pattern non vide & composé de strings.
  • Chaque symbole de pattern (hors .) doit exister dans legend.
  • legend.*.key référencent des ressources / items existants (warnings si manquants).
  • unlock.recipe_card_key doit être présent (erreur si manquant).
  • Si card_keys chargés → warning si la carte n’existe pas dans cards.yml.
# Depuis la racine du projet
python app/data/crafts/normalize_crafts_yaml.py

En cas d’erreur structurelle, le script :

  • affiche une liste d’erreurs;
  • n’écrase pas app/data/crafts.yml existant.

5. Workflow pour ajouter un nouveau craft

Étape 1 — Créer / vérifier l’item de sortie

  1. Ouvrir le bon fichier dans app/data/items/*.yml (ex: tools.yml).
  2. Ajouter une entrée sous items: avec une clé unique (ex: tool_shovel_basic).
  3. Remplir key, label, kind, icon, etc.

Étape 2 — Créer la carte de recette

  1. Choisir le fichier de fragments adapté, ex: app/data/cards/craft/recipes/tools.yml.
  2. Ajouter une nouvelle carte de type craft_recipe avec une key unique.
  3. Éventuellement lier card_gameplay.target_item_key à l’item créé.
  4. Configurer la partie shop (prix, visibilité).

Étape 3 — Déclarer la recette de craft

  1. Choisir la station/famille : ex. app/data/crafts/craft_base/tools.yml.
  2. Ajouter un bloc craft (slug = souvent la même chose que key).
  3. Définir :
    • station_key (ex: craft_table_base);
    • required_grid.tier (1, 2, 3…);
    • output.kind et output.key (ton item);
    • recipe.pattern / recipe.legend (matrice de craft);
    • craft_time_seconds et xp_reward;
    • unlock.recipe_card_key (la carte créée en Étape 2).

Étape 4 — Normaliser et vérifier

  1. Depuis la racine du projet, lancer : 
    python app/data/cards/normalize_cards_yaml.py
python app/data/crafts/normalize_crafts_yaml.py
  2. Corriger les éventuelles erreurs / warnings (items manquants, carte absente, symboles non définis…).
  3. Lancer le jeu et vérifier que la recette apparaît bien dans l’UI de craft.
Quand tu auras des centaines de recettes, ce workflow pourra être encapsulé dans une UI d’édition, mais la structure YAML restera la même. Cette doc sert de référence “canonique” pour le format.
